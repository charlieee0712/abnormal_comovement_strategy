# exec_briefs 协议 —— 规划 session ↔ 执行 session

用途：本目录是 `C:\Users\cnc\resonance_strategy` 下两个 Claude Code session 的交接面。规划 session 写编号 brief（E0、E1……），执行 session 按 brief 干活并交回同名 REPORT。两个 session 共用同一份 memory（同项目路径），memory 入口条目 = `resonance-engine-fix-calendar-timing-adjustment`。

## 文件约定
- `E<n>_<主题>.md`：规划 session 写。结构固定：0 背景 / 1 起点确认 / 2 做什么 / 3 自测与验收 / 4 交回 / 5 禁区。
- `E<n>_REPORT.md`：执行 session 写。结构固定：
  1. 起点确认逐项结果
  2. 做了什么（文件 + 函数 + 改动量级；新建文件列全名）
  3. 自测/验收逐条 PASS-FAIL 与**实得数字**（从日志 grep，不凭记忆）
  4. 锚点：results 目录名、日志路径、commit 哈希
  5. 纯文本摘要（≤15 行，可直接复制给网页版 Claude）
  6. BLOCKERS：现象 + 数字 + 你认为的原因 + 建议；没有就写"无"
- 出现 BLOCKER 即停：不改判据凑数、不自行外推、不跑 brief 没写的东西。

## 三方工作流（2026-09-04 起加入 Claude web）
- 规划 session 出每一轮 **proposal** → Claude web 参考 proposal 出 **plan**（设计层；web 看不到 47、跑不了代码）→ 规划 session 审 plan、写成最终 **brief**（含自审记录）→ 执行 session 执行。
- web 的 plan 落成文件 `exec_briefs/plans/<步骤>_plan_web.md`（用户带回），审后的最终 brief 仍是 `exec_briefs/E<n>_*.md`。
- web 的知识库 = `handoff_i11/`（≤40 个 .md；手写件 00–06、10 由规划 session 维护，其余由 `scripts/build_handoff_i11.py` 生成；只在用户说"更新"时重生成）。

## 规划 session 纪律（2026-09-04 用户定）
- **探索从宽、采纳只在 OOS 与用户过目**：brief 里不预筛、不按单因子强弱淘汰，统计量作列不作闸，"规则"写成"扫描 + 建议清单"。
- **写好先自审再上传**：按四类穷举下一轮可能的不利因素（代码/数值、统计/设计、运行/操作、解读），逐条给缓解，能改的直接改进 brief；确认方向与细节无误后才上传。brief 末尾固定一段 **「自审记录」**（不利因素 → 处置）。
- **执行端见到「自审记录」段才开工**；没有这段的 brief 视为未定稿，回退给规划 session。

## 执行 session 固定纪律（摘自 47 `PROJECT_STATUS.md` §11/§14/§15，只重申最常踩的）
1. 接手先读 47 `/mnt/sda2/lichenchen/code/project_core/PROJECT_STATUS.md` 全文 + memory 入口条目，再读 brief。
2. 四个地基文件 `data_loader.py / features_daily.py / event_study.py / pool_screening_v2.py` 只读；`results/` 下任何目录不删；不改 I11 信号/池/权重定义。
3. 长任务：`nohup taskset -c 96-191,288-383 python -u <脚本> > <日志> 2>&1 &` 然后 `disown`。47 的 socket 0（CPU 0-95、192-287）纯计算慢 8-10 倍（2026-09-02 定案），一律绑 socket 1。预计 >30 分钟的任务先报告再跑。轮询只看日志尾部，间隔 ≥60 秒。**并发进程数以 brief 写明的上限为硬约束**（未写则 ≤32，BLAS 单线程）；需要提高时先向用户报具体数字并获批，不得超过获批值（2026-09-07 E6e 阶段 E 一次放到 128 撞满共用机的进程配额，立此条）。分片长任务用任务状态表（PENDING/RUNNING/SUCCEEDED/FAILED/LIMIT）按 task_id 计数之和 = 登记总数来监控，只盯 DONE 计数看不出僵住的进程；完成状态由**父进程验收产物（hash/行数/退出码）后写 DONE**，worker 正常 close/join/flush 后退出，`os._exit(0)` 只作孤立 worker 的受控恢复手段、不作默认（2026-09-09 按 E6f web plan 改）。
4. 结果一律进 `/mnt/sda2/lichenchen/results/<时间戳>_<后缀>/`。数字只从 results 目录 / 日志 grep 出来，不从记忆或摘要抄。
5. 每个 brief 完成后在远端 `/mnt/sda2/lichenchen/worklog/WORKLOG.md` 末尾（正序）append 一条操作记录，并把同一段文字 append 到本地 `_tmp_WORKLOG.md`。worklog 不进 git、不 commit。只记操作层事实（跑了什么、改了什么、结果目录、commit、一句客观结论），理解性内容不写。
6. git：`abnormal_comovement_strategy` 直接提交 main。仓库是 PUBLIC（2026-09-02 核实，与 PROJECT_STATUS §1 记载不符）；用户与领导确认公开无妨（2026-09-02），**可以 push**。brief 里写了 push 才 push。
7. 文档表达规范：任何 .md / 脚本文案 / 日志 / memory / REPORT 里**不得出现登录信息**（口令、密钥、带账号的连接串）；主机只写别名（47 / 56），不写 IP、端口、用户名。看到私有文件或旧文档里的登录信息也不得转抄。
8. 给领导的数字必须经用户过目；REPORT 里不替用户下"可以交付"的结论。
9. 上下文纪律：读大文件先 `grep -n` 定位再 `sed -n a,bp` 取段；要改的函数整段读完再改；远端输出裁到 ≤20 行。建议在 scratchpad 建 `STATE.md`（≤40 行：目标 / 待办 / 锚点 / 已定数字 / 下一步命令），每个里程碑更新，compaction 后先读它。
